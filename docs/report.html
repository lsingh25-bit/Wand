1   Executive summary and status

This report describes a self-contained wearable wand that recognises five spell gestures and, equally importantly, refuses to recognise anything else. All sensing, signal conditioning, neural inference and decision-making run on a single ESP32-WROOM-32. Nothing is offloaded; the demonstration firmware does not contain a call to Serial.begin() at all.

Motion is captured by a BNO055 running in IMU fusion mode, which does its own sensor fusion on an onboard Cortex-M0 and returns gravity-free linear acceleration, bias-compensated angular rate, and an orientation quaternion at 100 Hz. That quaternion is what the rest of the design is built around: every gesture is rotated into the frame the wand occupied at the instant the caster began, which decouples translation from rotation instead of leaving them entangled the way a raw body-frame representation does. The resulting 64×12 tensor is classified by a 7,174-parameter depthwise-separable 1-D CNN, quantised to int8, into four compulsory spells, one bonus spell, and an explicitly trained NOISE class. A five-stage rejection cascade wraps the network and decides whether to fire at all.

The wand is a 500 mm tube. The ESP32 and the power system live at the butt, where the hand grips; the OLED faces the caster from mid-shaft; the BNO055 is mounted 130 mm below the tip with its +X axis running along the shaft towards the tip; the eight-LED ring is at the tip itself. That geometry is not packaging trivia and it is not confined to §3 — it is an input to the signal model. A sensor bolted 370 mm from the caster's hand does not measure the hand; it measures the hand plus a lever arm, and for every gesture in this vocabulary the lever term is three to ten times the larger. R4 exists because the previous revision's bootstrap generator did not know that.

1.3   What changed in revision R4: the wand became part of the model

R3 was correct about the sensor and silent about the object it is bolted to. The bootstrap generator that de-risked the whole pipeline described each spell as two independently hand-tuned curves: an angular rate programme, and, separately, an acceleration programme. Nothing connected them.

That is not a small liberty. It is the wrong physics, and it is wrong in the direction that flatters the model. On the real wand the accelerometer channel is very nearly a deterministic function of the gyro channel, because the sensor is 370 mm up a rigid shaft from a hand that is 80–330 mm behind it. A generator that treats acceleration as free hands the network a channel carrying independent information that the hardware will never provide, and the network learns a decision rule that does not exist.

R4 replaces those curves with rigid-body kinematics driven by the measured geometry (§4.2). The caster's motion is now specified as the two things a human actually commands — how the wand rotates, and where the hand goes — and everything the accelerometer sees is derived. Four consequences followed immediately, and none of them were anticipated:

ConsequenceWhat it changed
The accelerometer divisor was wrongNORM_ACC_LIN was 3.0 on the reasoning that "gravity consumes 1 g of the 4". Gravity is subtracted, so it extends the range rather than eating it: the true bound is 5 g and the corpus reaches exactly that. At 3.0 the tensor railed on 2.4% of all samples, including the peak of every sharp flick — the part that identifies the gesture (§6.5).

Three of the four are defects that existed in R3 and were invisible to every test R3 had. They became visible the moment the synthetic data started obeying the same physics the hardware does. That is the argument for modelling the object rather than the signal, made concretely rather than in the abstract.

R4 also consolidated the firmware. The tree had accumulated two incompatible BNO055 implementations — the fusion driver the whole pipeline is built on, and a second one running the chip as a plain 6-axis sensor, each defining a struct called RawSample with different fields. Neither was reachable from a build, so nothing failed. There is now exactly one driver, in firmware/common/, and all three firmware targets link it (§10.1).

3.2   The levers, in the order they should be pulled

  1. Ask the coordinators whether a club-borrowed or already-owned BNO055 counts against the cap. This question was already open and is now the single most consequential one on the project. It is a five-minute conversation and it decides whether any of the following is needed.
  2. Source a generic GY-BNO055 rather than a branded breakout. Unbranded modules list substantially below the 7Semi and ThinkRobotics prices. Same silicon; verify CHIP_ID reads 0xA0 on arrival, because clone modules in this family sometimes carry a different part.
  3. Drop the battery path (₹365) and run from a USB power bank housed in the handle. This preserves the on-device-inference claim completely — a power bank carries no data lines and cannot receive an offloaded computation — but it is visually weaker and invites a question from a judge, so it is third rather than second.
  4. Drop the buzzer (₹20) and the enclosure spend (₹80) in favour of cardboard or a wooden dowel, which the problem statement explicitly permits. Saves ₹100 and costs presentation marks; a last resort.

What should not be cut is the OLED: the problem statement requires the latency variable to be printed on screen, so it is a compliance item, not a decoration.

3.3   IMU configuration and the reasoning for each value

These register writes are part of the frozen contract with the training data. Unlike the MPU-6050, none of them is a range setting — in fusion mode the algorithm owns the ranges — which removes an entire class of silent error, where a scale constant and a register drift apart and every capture is quietly rescaled.

Why the boost is set to 4.50 V and not 5.00 V. This single change removed both diodes from the design. A WS2812's logic threshold is approximately 0.7×VDD; at 5 V that is 3.5 V and the ESP32 only drives 3.3 V — marginal on a cool bench, and a source of dropped pixels once the chip warms up mid-demo. The original fix was a diode in the ring's supply. Setting the whole rail to 4.50 V puts the threshold at 3.15 V, which 3.3 V logic clears, while still leaving the AMS1117 about 1.2 V of headroom to produce 3.3 V. One trimpot turn replaces a component.

Set the MT3608 before connecting anything to its output. These ship at arbitrary settings and can arrive well above 5 V. Battery and switch on the input, output bare, multimeter on the output, turn the trimpot until it reads 4.50 V.

Why two I2C buses. Pushing a full 128×64 frame to the SSD1306 occupies its bus for 25–30 ms. Sharing a bus with the sensor would mean the sampler simply cannot read for that window, and the resulting gaps in the 10 ms grid are invisible: the logger keeps producing well-formed CSV throughout. Bus separation removes the contention, pinning the display to core 1 removes the CPU contention, and the firmware additionally never touches the display while a capture is active. Three independent defences against one silent failure.

Star grounding. Every ground returns to one point, and the LED ring's return gets its own wire rather than being daisy-chained. Ring current through a shared ground wire creates offsets that couple into the sensor as noise — and with a fusion sensor that noise does not merely add to the output, it degrades the orientation estimate that the entire feature representation is built on.

Why GPIO27 for the trigger. It is not a strapping pin. GPIO 0, 2, 12 and 15 are sampled at reset to select boot mode, so a trigger on any of those would drop the board into firmware download mode if a judge happened to be holding it at power-on.

Why the BNO055 goes at 37 cm and not next to the ESP32. Three reasons, in order of weight. Signal: acceleration at the sensor scales with the lever arm, so a sensor near the hand sees a fraction of the motion and the accelerometer channels become mostly noise. Interference: the ESP32's WiFi front end, the boost converter's switching node and the battery's charge current are all at the butt, and the BNO055's fusion output degrades with supply noise rather than merely getting noisier. Rigidity: the sensor must not move relative to the shaft, and a short unsupported span near the tip is easier to bond solidly than a crowded compartment.

Why the LED ring goes past it, at the tip. The ring is the feedback the caster and the judge actually look at, and at the tip it reads as the wand casting rather than as a board blinking. The cost is that its supply and data wires run the length of the tube, past the sensor. They are twisted with their own return and the ring's ground goes back to the star point on its own wire, because ~150 mA of switched LED current sharing a ground with the sensor is exactly the disturbance that shows up as orientation drift.

Why the OLED sits at 22 cm. It has to face the caster while the wand is held, which puts it in the middle third; further forward and the hand covers it, further back and it points at the floor when the wand is raised. It is also the heaviest thing that is not the battery, so keeping it behind the sensor keeps the balance point behind the grip.

Two mounting facts the software cannot check for itself The sensor's +X must point at the tip and the board must be rigidly bonded. If +X points at the butt, every derivation in §4.2 describes a mirrored wand; if the board can shift a few degrees in its mount, the anchor drifts between the pre-roll and the cast. Neither shows up in the data as anything but slightly worse accuracy. Test 5 of the bring-up suite (§13) checks the axis directly, by pointing the tip at the floor and reading the gravity vector out of the quaternion — body-frame "up" should come back as approximately (−1, 0, 0).

4   Spell vocabulary, kinematic definitions, and the lever-arm model

Directional definitions are fixed in the wand's own body frame: +X along the wand towards the tip, +Y to the caster's left, +Z up through the back of the wand. The sensor is mounted with X along the shaft and Z out of the PCB face, 370 mm forward of the butt (§3.5). One sign convention is worth stating explicitly because it catches everyone: by the right-hand rule about +Y with +Z up, a positive pitch rate carries the tip downward. Every "tip up" move in this document therefore carries a negative pitch excursion, and the code is written that way rather than with a flipped axis, so that the frame stays the one the firmware uses.

4.1   Why Stupefy is the right bonus spell, and the trap it sets twice

Stupefy was not chosen for flavour. The four compulsory spells all consist of rotation, and three of the four contain a terminal flick, so they occupy a similar region of feature space and compete with one another. Stupefy is defined as a thrust with almost no rotation, which places it in an otherwise empty region: it adds a class without crowding the existing ones. It also provides a free integrity check — its peak angular rate should be several times smaller than every other spell's, and if that ordering ever inverts, the labels have been shuffled.

The same property that makes it a good bonus spell has now caused two separate false-rejection defects in the plausibility gate, both caught on the bench and both documented in §8.3. Anything that pre-filters on "is this energetic enough to be a spell" will, if written carelessly, silently delete the one spell whose signature is not rotational.

4.2   The wand is a lever, and that dominates the signal R4

Everything above describes what the caster does. What the sensor records is a different quantity, and the difference is the 370 mm of tube between the two. For a point rigidly attached to a rotating body, its acceleration is

a_sensor  =  a_pivot   +   α × r   +   ω × (ω × r)
             \______/       \_____/       \____________/
              the hand        Euler         centripetal
              travels        (angular       (always inward,
                              accel)         always present)

where r is the fixed vector from the centre of rotation to the sensor, and all three terms are expressed in the sensor's own frame. The BNO055's linear-acceleration registers report exactly this quantity, because the fusion has already removed gravity.

The centre of rotation is a property of the caster, not the wand. A flick pivots at the wrist, roughly 80 mm behind the butt; a loop or a swish pivots at the elbow, roughly 330 mm behind it; walking swings the whole arm from the shoulder. Adding the sensor's 370 mm gives lever arms of 0.45 m, 0.70 m and 0.99 m — so even the shortest puts the BNO055 nearly half a metre from the point it is rotating about.

Put numbers to it. At the 6 rad/s a brisk flick reaches, the centripetal term alone is 0.45 × 6² = 16 m/s², or 1.7 g — from rotation, with the hand held perfectly still. The Euler term is larger still during the flick itself, because a 0.8 rad turn in 280 ms implies about 60 rad/s² and 0.45 m of arm turns that into 2.7 g. Meanwhile the caster's hand, travelling 200 mm in half a second, contributes about 0.2 g.

Three things follow that are not obvious without doing the arithmetic:

  • The accelerometer is mostly a second view of the gyroscope. Within each rotational class the correlation between peak |ω| and peak |a| measures 0.63–0.93 (§9.5). The channels are not independent, and a generator that made them independent was teaching the network a relationship the hardware will never show it.
  • Saturation is normal, not a failure. A wand this long genuinely drives the ±4 g rail on sharp casts. That is expected, it affects Alohomora and Wingardium Leviosa most, and it is precisely why the impact test keys on duration instead of magnitude (§8.3).
  • Grip position matters more than grip angle. A caster who chokes up on the shaft, or who flicks from the wrist where another swings from the elbow, changes r and therefore changes the acceleration amplitude by up to a factor of two — while the gyro channels barely move. That is modelled as a per-caster pivot scale in the bootstrap corpus and is one of the axes leave-one-caster-out validation is testing.
Where this model is approximate, stated plainly The pivot is treated as a single point on the wand's own axis, fixed for the duration of a gesture. Neither is exactly true: a real wrist sits slightly off the shaft's line, and a gesture that begins at the elbow and ends at the wrist moves its pivot mid-cast (Alohomora does exactly this, and is modelled with a pivot halfway between the two). Both approximations understate variety rather than inventing it, which is the safe direction. The quantity they get right — that the lever term dominates, and by how much — is the one the design depends on.

5   Data acquisition

5.1   Deterministic 100 Hz sampling

A hardware timer fires every 10,000 µs and does exactly one thing: release a binary semaphore. A FreeRTOS task pinned to core 0 at maximum priority takes that semaphore and performs the I2C burst.

The division of labour matters more here than it did with the MPU-6050. The 26-byte burst at 100 kHz is a blocking transaction of roughly 2.4 ms — nearly a quarter of the sample period. Performing that inside the ISR would block every other interrupt on the core for the whole time. The ISR does the one thing an interrupt handler should do, and the task does the work.

5.2   One burst, one fusion frame R3

Reading gyro, quaternion and linear acceleration in one transaction is not merely faster than three. It guarantees that every channel in a sample comes from the same fusion frame. With three separate reads the quaternion and the acceleration can straddle a frame boundary, producing a skew that varies with bus timing and cannot be corrected afterwards — and in a representation where acceleration is rotated by the quaternion, a one-frame skew is not a small error, it is a rotation applied to the wrong vector.

The six Euler bytes sit in the middle of the address range and so cannot be skipped in a burst. They are read and discarded; paying 0.5 ms for them is cheaper than splitting the transaction.

5.3   Three data-quality gates the sensor swap made necessary

Gyro calibration status. The fusion's continuously-estimated gyro bias is what replaced the software bias subtraction. Below CALIB_STAT gyro level 3 that estimate is not trustworthy, and every capture taken there is quietly wrong with nothing to indicate it. The firmware therefore refuses to arm until the level reaches 3 and shows the progress on the OLED, which turns an invisible precondition into something the caster can see and wait for.

Duplicate fusion frames. The BNO055's fusion output is also 100 Hz, but its clock is not phase-locked to ours, so the two beat against each other and a frame is occasionally read twice. This is harmless — at most one sample period of sample-and-hold, far below the noise floor once the gesture is resampled to 64 steps — but it is counted, because a high duplicate rate means something else is wrong: a stalling bus, or the chip having fallen out of fusion mode.

A quaternion that never moves. If the chip drops back to CONFIG mode, or is left in a non-fusion mode, the quaternion registers read constant or zero. The tensor would still have the right shape, the model would still train, and four of its twelve input channels would simply be dead. Nobody would notice. The collection script rejects any capture whose quaternion does not change.

5.4   Segmentation, and why the pre-roll matters twice as much now

The trigger button defines the gesture window: press and hold, cast, release. Behind it a 320-sample circular buffer runs continuously so the window can be extended backwards in time.

In R2 the pre-roll existed for one reason: casters begin moving fractionally before their thumb lands, and without it the first fraction of every gesture is clipped — consistently, in training and inference alike, so nothing ever looks broken. The model simply learns a truncated gesture.

In R3 it carries a second and heavier load. Sample 0 of the window is the anchor for the entire orientation representation. Every quaternion channel, and the frame that acceleration and angular rate are expressed in, is defined relative to it. It therefore needs to be taken while the caster is still holding their resting grip, not mid-motion, and the 200 ms pre-roll is what guarantees that.

5.5   Collection protocol: manufacturing variation deliberately

Left to themselves, people converge on one comfortable way of performing a gesture within about five repetitions. A dataset with one style per caster is precisely the overfitting the invariance test is designed to expose, so the collection script randomises the prompt for every repetition.

5.6   The collection firmware, and one wire format R4

firmware/wand_logger/ shares the sampler, the driver and every constant with the demo firmware. That is a requirement rather than a convenience: the model is trained on what the logger writes to the serial port and runs on what wand_infer.cpp reads out of its ring buffer, so any difference between the two is a distribution shift that no downstream test can see.

The CSV it emits is the contract. training/collect.py parses exactly this and nothing else, and parity_host reads the same rows back — change one column here and three other files are wrong with no compiler to say so.

The command channel runs the other way and is the same kind of contract: collect.py already sends SET label=<n> caster=<name>, so the firmware parses that rather than inventing a scheme of its own. A mismatch there does not fail — it files every capture under the wrong label, quietly, and the first symptom is a confusion matrix nobody can explain.

6   The signal processing chain

The chain converts a variable-length raw integer stream into a fixed 64×12 float tensor. It is implemented twice — once in Python as the reference, once in C++ for the device — and the two are asserted equal to 10−3 by an automated test (§9.2).

6.1   What the sensor already did, and why we let it R3

Three stages that R2 performed in software are gone. The BNO055's Cortex-M0 removes gyro bias continuously, runs a Kalman-class orientation estimator, and subtracts gravity — all three better than a 100 Hz complementary filter written by us, and all three for free in terms of ESP32 cycles.

The advice we were given was the opposite: put the chip in AMG (non-fusion) mode so the existing chain would not subtract gravity twice. The hazard is real — double subtraction produces no error message anywhere — but disabling the fusion is the wrong resolution. Three things are gained by deleting our chain instead:

  • Latency. The complementary filter and gravity projection cost roughly 920 transcendental calls per gesture, about 2.5 ms on Xtensa. The R3 chain contains no transcendental function at all on the hot path except the two sqrtf calls per sample for the magnitudes.
  • Correctness. Our filter recovered roll and pitch only; yaw is unobservable from accelerometer and gyroscope alone in that formulation. The chip's estimator produces a full quaternion.
  • Risk. The complementary filter's initialisation is, on the evidence of our own negative control (§9.2), the single easiest thing in this project to get subtly wrong. Deleting it deletes that risk.

What we give up is accelerometer range: AMG mode would permit ±16 g, fusion locks ±4 g. That trade is examined honestly in §8.3, and the conclusion is that clipping a thrust does not make it less distinguishable — it makes it more so, because no other class saturates.

6.3   Step 2: anchoring — the idea the whole representation rests on R3

The chip reports linear acceleration and angular rate in the sensor body frame — a frame that rotates with the wand as the gesture is performed. That is the natural output and it is also the problem: a constant push in the world appears as a time-varying signal in a spinning frame, so translation and rotation arrive at the network tangled together, and the network has to spend capacity disentangling them before it can start recognising anything.

Because we also have the orientation, we can undo that. Define

q_rel[i] = conj(q[0]) ⊗ q[i]

a_anchored[i] = rotate(q_rel[i], a_body[i])
ω_anchored[i] = rotate(q_rel[i], ω_body[i])

and every quantity is now expressed in the single fixed frame the wand occupied at sample 0. Channels 0–2 become pure translation in a frame that does not spin; channels 3–9 carry the rotation, explicitly and separately. The two are decoupled.

There is a useful side effect. q_rel[0] is the identity by construction, so channel 6 always starts at exactly 1.0 and channels 7–9 at exactly 0.0. Every gesture begins at the same point in the representation, and the convolutions only ever have to model the departure from it. That fixed starting point is relied on downstream: the augmentation pipeline re-establishes it after every transform (§7.4), and a unit test asserts the channel layout that makes it meaningful.

What anchoring does and does not buy — stated precisely Anchoring removes which way the caster was facing. It does not remove how they were holding the wand, because the anchor rotates with the grip: a caster whose wrist is rolled 30° further has an anchor rolled 30° further too. Grip variation is handled separately, by the augmentation in §7.4, and the two mechanisms are complementary rather than redundant. It would be easy to overclaim here and we are not going to — the invariance test will be run by people whose grips we have never seen.

6.4   Quaternion sanitising: three hazards that all look like valid data

The hemisphere continuity pass is the one that would be easiest to omit and hardest to debug. A quaternion double-covers rotations — q and −q are the same orientation — and the chip is free to return either. Without the continuity pass, channels 6–9 contain sign discontinuities that look like instantaneous 360-degree rotations, and no convolution can learn through that. Our negative control for this exact omission produced a parity divergence of 1.92, roughly two thousand times the tolerance (§9.2).

6.5   Steps 3 and 4: resampling and normalisation

Resampling produces speed invariance: a 0.6-second Lumos and a 1.4-second Lumos both become 64 steps, so the network sees the shape of the trajectory and is structurally blind to how fast the judge happened to wave. Interpolation is in index space rather than time space, because the logger already guarantees a uniform 10 ms grid and index space reduces to two multiplies and an add in C++, with no floating-point time accumulation that could diverge between implementations.

The quaternion channels are interpolated linearly rather than by slerp, and deliberately not renormalised afterwards. Between adjacent 100 Hz samples the rotation is under a degree, where lerp and slerp differ by less than 10−5; a renormalisation step would be one more place for the two chains to disagree, in exchange for a correction smaller than the sensor noise.

Normalisation is deliberately not a per-sample z-score. Amplitude is a real discriminative feature here — Stupefy is a hard ballistic thrust and Wingardium Leviosa is a gentle swish, and z-scoring makes them look alike — and a per-sample statistic would force the MCU to buffer the gesture, compute mean and variance, and walk it again. Fixed divisors are one multiply per sample.

The divisor that was derived with the sign the wrong way round R4

R3 set NORM_ACC_LIN = 3.0 and wrote a unit test asserting it, on this reasoning: the fusion locks the accelerometer to ±4 g, gravity consumes one of them, therefore 3 g is the ceiling. The reasoning is confident, it has an assertion behind it, and it is wrong. Gravity is subtracted by the fusion, not spent from the budget. The rail applies to the raw signal, before that subtraction:

lin_axis  =  raw_axis  −  g_axis,     raw_axis ∈ [−4, +4] g,   g_axis ∈ [−1, +1] g
          ⇒  lin_axis ∈ [−5, +5] g

So the reportable range is the rail plus one gravity. The measured per-axis maximum across the bootstrap corpus is exactly 5.00 g — the arithmetic above, reached and not exceeded, which is as clean a confirmation as this kind of derivation gets.

This mattered. At 3.0 the tensor railed on 2.4% of all samples, and not at random: the samples that clip are the peaks of the sharp flicks, which is the part of the trace that identifies Alohomora and Wingardium Leviosa. The divisor is now 5.0 — a hard physical bound, so nothing clips and no int8 code is spent on a value the sensor cannot produce — and railing fell to 0.08%. The unit test was rewritten to assert the corrected relationship, and it is worth noting that the old test passed throughout: an assertion is only as good as the derivation behind it, and this one had been guarding the wrong inequality with complete conviction.

The gyro divisor was re-examined in the same pass and deliberately left alone. The corpus reaches only 0.43 of NORM_GYRO at the 99th percentile, so tightening it to 9 or 10 would buy ~20% more int8 resolution on the quiet part of every gesture. It would buy that by railing the samples out at the tail — which are the peaks of the flicks, and the presence and sharpness of a terminal flick is the entire difference between Alohomora and Lumos. Measured, considered, unchanged.

7.2   Flatten rather than global average pooling

Most TinyML classifiers of this size end in global average pooling, which would have saved 4,096 weights. It was rejected deliberately. Pooling discards when each feature occurred, and when is exactly what separates Alohomora (backward loop, then flick) from Wingardium Leviosa (lateral swish, then flick): both contain a broad sweep and a terminal flick, differing in order, direction and relative timing. A pooled representation sees "one sweep, one flick" for both; a flattened one retains the ordering across the eight remaining time steps.

The cost is 4,096 additional int8 weights, which on a chip with 520 KB of SRAM is not a real cost. This is a concrete instance of a general principle in this design: spend memory, which is abundant, to protect accuracy and latency, which are not.

7.3   Training regime

Label smoothing at ε = 0.05 prevents the network driving its softmax to 1.0 on the training casters. Over-confidence is not cosmetic: an over-confident model is confidently wrong on an unseen hand, and it makes every rejection threshold useless because all probabilities land above whatever value you pick. §8.4 documents the concrete consequence and how it is handled.

Class weighting is inverse-frequency with the NOISE weight nudged up a further 1.25. That extra factor encodes the scoring asymmetry directly into the loss: under this problem statement a missed spell scores nothing while a misfire is penalised, so the training objective should not treat the two errors as equal.

7.4   Augmentation as manufactured invariance R3

With five casters there are five hand-writing styles in the dataset. The judges will be a sixth, seventh and eighth. That gap cannot be collected away in the time remaining, so augmentation manufactures the between-caster variation that could not be recorded. Every transform is physically exact rather than generic noise — an augmentation that produces impossible signals teaches the network to separate real from impossible instead of Lumos from Alohomora.

The conjugation is the part worth being careful about, and it is new in R3. q_rel is a rotation expressed in the anchored frame, and rotating the frame itself is a change of basis, which for rotations is conjugation — not a left-multiply. Left-multiplying, the obvious-looking mistake, would compose an extra rotation into the gesture and produce trajectories no wrist could perform, and the network would learn to detect the difference between real and augmented instead of the difference between spells.

Keeping the tensor internally consistent

Two further R3 subtleties, both of which would produce a self-contradictory tensor if ignored:

Scaling the rate without scaling the orientation. If the magnitude augmentation multiplies the angular-rate channels by 1.2 but leaves the quaternion channels alone, channels 3–5 describe a rotation that channels 6–9 do not perform. The network would happily learn to detect that contradiction. So the relative quaternion's rotation angle is scaled by the same factor, about the same axis.

Moving the anchor. A negative time shift drops early samples, so the new first sample is no longer the identity and the invariant that every real tensor satisfies is broken. Rather than forbidding the transform, a re-anchoring step runs once at the end of the pipeline and restores it.

7.5   Int8 quantisation, and what it actually cost

Full-integer quantisation with int8 input and output was chosen over float16 or dynamic-range for three reasons: TFLM's int8 kernels run several times faster than float on the Xtensa LX6; int8 input means the firmware never allocates a float input buffer, because preprocessing writes quantised bytes straight into the arena; and weights are four times smaller, which here is a bonus rather than the point.

A twelve-channel tensor raises a legitimate concern that eight channels did not. TFLite uses a single per-tensor scale for the input, and the quaternion channels use the full [−1, 1] range while the anchored acceleration channels are much smaller — so the acceleration channels could in principle be crushed to a handful of quantisation levels. 8   False-positive rejection: the Muggle Movement defence

8.1   Why a trained NOISE class, and not a confidence threshold

The obvious approach — train on four spells and reject anything below a softmax threshold — fails for a structural reason rather than a tuning reason. A softmax over four classes must sum to one. Shown a shrug, such a network has no way to express "none of these"; it is forced to distribute its belief across four spells, and it frequently lands on one of them with high confidence. No threshold fixes this, because the problem is that the model has nowhere to put the probability mass.

Giving NOISE its own trained output gives the network somewhere to put it. The difference is between a threshold hack applied to a model that cannot represent the concept, and a classifier that has actually learned what "not a spell" looks like — including what a half-completed spell looks like, which no unsupervised outlier criterion will ever catch.

8.2   The five-stage cascade

Stages are ordered cheapest first: there is no reason to spend milliseconds of inference establishing that someone scratched their nose. Every stage can only ever turn a fire into a no-fire; none can invent a cast.

8.3   Five defects in one subsystem, found and fixed before any data existed

Stage 1 is forty lines of comparisons and it has now been wrong five separate times. That is not a comment on the people who wrote it; it is what a threshold does when it is chosen by reasoning about a signal instead of measuring one. Each fix is below, in the order they were found.

Defect 1 — the bonus spell was unreachable (R2). The first plausibility gate applied a single peak-rotation floor and rejected 100% of Stupefy, because Stupefy is defined as a thrust that barely rotates. The property that makes it a good bonus spell was exactly what the gate threw away, and the network never saw one. On the bench this looks like a model that cannot learn Stupefy.

The fix is a disjunction rather than a conjunction: a window is plausible if it is rotationally energetic or ballistically energetic. Scratching and pacing are neither, which is what keeps the pair separable.

Defect 2 — the impact test was unreachable (R3). With the MPU-6050 at ±8 g, a 7.5 g table knock was separable from a 3 g cast by magnitude alone. The BNO055's fusion locks the accelerometer at ±4 g, so a knock and a hard Stupefy both saturate near 3 g. In our bootstrap corpus 65% of Stupefy captures reach the ceiling. Magnitude can no longer separate them.

Duration can, and always could. A collision reaches the spike level for one or two samples and is gone; a thrust holds it for tens. The test became: a window is an impact if it reaches the spike level but never holds it.

Defect 3 — the replacement test, chosen by intuition, rejected 9% of Stupefy. Having designed a better test we then set its two constants by feel (2.40 g, 4 samples) and made the same class of error a third time. Sweeping the pair moved it to 2.00 g, where it rejected no spells at all and caught five times as much noise. The intuitive setting had been worse on both axes simultaneously. That is the argument for sweeping rather than guessing, in one line.

Defect 4 — that sweep's grid stopped below the answer R4. The sweep ran levels from 1.6 g to 2.4 g, because R3 believed 3 g was the physical ceiling. Once §6.5 corrected the reportable range to 5 g, that ceiling turned out to be inside the search space rather than outside it — and a sweep whose grid stops short does not report that it stopped short. It reports a winner, with the same confident formatting as a sweep that searched the whole space. The grid now runs to 4.4 g and the selection rule takes a small budget of spell loss rather than demanding exactly zero, because with realistic lever-arm physics a gentle cast from a light-handed caster genuinely lands near the threshold and a hard zero-loss constraint just picks whichever corner of the grid happens to be degenerate.

8.4   Thresholds are measured, not chosen

The confidence and margin thresholds started as intuition: 0.80 and 0.25. The diagnostic run that followed produced the most useful single result of the bring-up phase — a model that was 100% correct by argmax while the confidence gate discarded more than half of its answers.

The cause is structural. With label smoothing at ε = 0.05 over six classes, the training target for the correct class is 1 − ε + ε/K = 0.958, and a converged model's honest top-1 probability sits well below that. On the R3 model the highest softmax value observed anywhere in the corpus was 0.660. A threshold of 0.80 is therefore not conservative — it is unreachable, and it presents as a broken model.

The response was not to pick a better number by hand but to remove the number from the design. The three softmax thresholds now live in shared/wand_thresholds.h, generated by training/calibrate.py from the pooled leave-one-caster-out probability distribution, carrying a WAND_THRESHOLDS_CALIBRATED flag that a unit test checks. The selection rule encodes the scoring asymmetry: highest recall whose out-of-sample misfire rate is still zero, breaking ties toward the larger margin, because margin failures are the Lumos/Alohomora confusions and those are the ones a judge will reproduce deliberately.

9   Validation methodology

9.1   Leave-one-caster-out, and why not a random split

A random split places repetitions from the same person on both sides of the line, so the model can memorise that person's idiosyncratic wrist signature and still look excellent. The judges are strangers. LOCO tests the only question that matters — does this work on a hand it has never seen — and it will read several points lower than a random split. That lower number is the one worth reporting, because it is the one that can be defended when a judge picks up the wand. A sixth caster's data is additionally held out entirely and never enters any training or calibration loop, as a check against the LOCO procedure itself having been tuned against.

9.2   The Python/C++ parity harness, and two negative controls

This is the most valuable test in the repository. Every other bug in this project announces itself: a wiring fault gives no I2C device, a bad build flag fails to compile, a bad model gives visibly wrong classes. A preprocessing divergence gives none of that. Both chains run clean, the training accuracy is excellent, the firmware is fast and stable, and the wand classifies at chance. There is nothing to grep for and no error to read.

The schedule trick that made this available on day one This check is normally described as something you run once the hardware works and real gestures exist — which places the project's highest-risk defect at the end of the timeline. 9.4   The synthetic quarantine

The bootstrap generator is what allowed the entire pipeline — tensor shapes, quaternion anchoring, augmentation, the network graph, int8 conversion, the C array export, arena sizing, the parity harness, and the threshold calibration path — to be built and proven before any gesture existed.

It is not a dataset, and three independent locks enforce that: output goes only to data/synthetic/ and the generator refuses any path containing raw; every file carries a # SYNTHETIC first line and every row a synthetic=1 column; and the loader refuses to run unless data/raw holds at least 50 genuine captures, or --allow-synthetic is passed explicitly — in which case every printed number is prefixed SYNTHETIC -- NOT A RESULT.

The bootstrap corpus produces argmax accuracy of 0.999 ± 0.003 across the six held-out folds. That figure is reported here only as evidence that generated data is trivially separable and therefore worthless as a result. It is the same signature — near-perfect scores, near-zero variance — that this project has already been misled by once.

9.5   Making the generator obey the wand's physics, and auditing that it does R4

Better physics does not make a synthetic corpus into evidence. What it makes it into is a usable engineering target: the tensor ranges, the saturation rate, the gate pass rates and the arena size become the ones the real wand will produce, so every constant sized against them is sized against something real. Everything in §6.5 and §8.3 came out of that change, and none of it was reachable before.

What the caster commands, and what is derived

Each spell is now specified as a sequence of angular excursions in radians and hand displacements in metres, over named fractions of the gesture duration. There is not a single acceleration constant anywhere in the spell definitions, and there must never be one: the moment somebody adds one, the accelerometer channel stops being a consequence of the gesture and goes back to being a free parameter.

Both commanded quantities use the minimum-jerk profile s(u) = 10u³ − 15u⁴ + 6u⁵ (Flash & Hogan, 1985), the standard model of human point-to-point limb movement. It is not chosen for elegance: its first derivative is zero at both ends, and so is its second. A profile with non-zero endpoint acceleration would inject a step into α, and therefore a discontinuity into the accelerometer channel, that no real arm produces and that 100 Hz sampling would alias. Specifying rotations as excursions also means the rate profile integrates to exactly the requested angle, which is a quantity that can be checked against a video of someone casting — as a hand-picked amplitude in counts cannot.

Everything the sensor sees then follows from the rigid-body relation of §4.2. Note where the ±4 g clip is applied — to the raw signal, before gravity is subtracted, because that is where the chip applies it. Clipping the linear channel directly would be wrong by up to 1 g and would understate how often a hard cast actually saturates.

One detail in there is worth pointing at, because getting it wrong produces a defect that looks exactly like a hardware fault. The pre-roll and post-roll pad the angular rate with zeros but pad the hand path by holding its endpoint value. Padding a position with zeros injects a step, and the second derivative of a step is an impulse — so every single capture would have carried a phantom impact at the seam, in exactly the shape the Stage 1 impact test is built to detect.

The audit: physics is checkable, and "it looks about right in a plot" is not a check

training/audit_corpus.py reduces a corpus to the quantities that can be checked against arithmetic and a stopwatch, and states a pass or a warning against a band for each. Every band is a property of a person waving a 50 cm stick rather than of this project's model, so the same script is the acceptance test for the real corpus once it exists. If the real numbers fall outside these bands, the bands were what was wrong, and the synthetic corpus tuned to them has to be regenerated before it is used to size anything.

10   Firmware implementation walkthrough

10.1   One driver, three firmwares R4

The BNO055 driver lives in firmware/common/bno055_fusion.cpp and is linked by all three targets: the demo firmware, the logger that produces the training data, and the bring-up suite that decides whether the sensor is trustworthy at all. That sharing is the point rather than tidiness. A bring-up tool that configures the chip its own way tests a configuration that will never be flashed again, and the acceptance it grants is worthless; a logger that configures it differently from the demo firmware produces training data from a sensor the demo will not be using.

The hazard this consolidation removed The tree had accumulated two incompatible BNO055 implementations: the fusion driver, and a second one running the chip as a plain 6-axis sensor in ACCGYRO mode with its own six-field RawSample — same struct name, different fields, different units. Neither was reachable from a build, because build_src_filter happened to exclude both directories, so nothing failed and nothing warned. The moment anyone changed a filter, the firmware would have filled a fusion-shaped struct from raw accelerometer registers and classified at chance, with no error anywhere. The non-fusion path is deleted; its two genuinely good ideas — named InitResult failure causes rather than a bool, and read-back verification on every configuration write — were kept and are visible in the code below.

10.2   Sensor bring-up, and an assumption converted into a check

A silent-failure mode found late, from a parallel implementation The BNO055 has two register pages, selected by PAGE_ID at 0x07. This design never writes a page-1 register — in fusion mode the algorithm owns the ranges — so it initially looked like a non-issue. It is not: UNIT_SEL (0x3B) and OPR_MODE (0x3D) are page-0 addresses. A chip left on page 1 by an earlier experiment, or by a reset partway through someone else's configuration sequence, would silently discard both writes, and the wand would run in whatever mode and units it happened to be left in — with the sensor streaming perfectly plausible numbers and nothing anywhere reporting a problem. One register write closes it, and every configuration write is now read back and verified rather than assumed. Claiming to guard against a dropped write without reading it back is not a guard.

Two further details are deliberate. The power-on wait is a poll rather than a blind delay: the chip does not answer I2C at all for about 650 ms, but a bare delay would also hide the case where the sensor is genuinely absent, and that should fail loudly at boot. And UNIT_SEL is written even though 0x00 is its power-on default, because a chip left in mg or rad/s by an earlier experiment would silently rescale every capture with nothing downstream reporting an error.

The datasheet states that the quaternion registers are valid in every fusion mode. "The datasheet says" is exactly the kind of claim this project checks rather than trusts, because if it were wrong the failure would be silent — the quaternion would read zero, the preprocessing would substitute the identity, four of twelve channels would be constant, and the wand would simply classify worse:

10.3   The TFLM operator resolver and inference

A MicroMutableOpResolver listing exactly the seven kernels this graph uses, rather than AllOpsResolver — the latter links every kernel TFLM has, well over 100 KB of flash for operations this model will never execute. Naming them also means an accidental architecture change that introduces a new operator fails loudly at AllocateTensors() instead of silently bloating the binary. The added s_in->bytes check is an R3 guard: a model retrained with a different channel count against firmware that was not rebuilt would otherwise read past its input tensor.

10.4   A window of stale data that passed the duration gate R4

The ring buffer holds 320 samples — 3.2 seconds. The capture window holds 230. Hold the trigger for six seconds and the requested window is 600 samples long, of which the first 280 have been overwritten.

The original code clamped the count to the window capacity and then read from the original start position. So it returned 230 samples of unrelated history, spliced across the ring's write pointer, carrying a duration of exactly 2.30 s — which is REJ_MAX_DURATION_S, and the bound is a strict >. The window passed the duration gate and went to the network. A garbage window that gets rejected is a non-event; a garbage window that gets classified is a spell nobody cast, in front of a judge, from a wand that was simply being held.

Two changes, deliberately overlapping. The caller now rejects an over-long hold where the true held length is still known — once the count has been clamped, that information is gone and every over-long hold looks like an ordinary 2.3-second gesture. And the function independently refuses to read data the ring can no longer vouch for. The two failures look identical from outside and only one of them announces itself, which is the argument for having both.

12   On-device processing compliance

The problem statement specifies immediate disqualification if serial communication is used to offload inference. Three independent measures address this:

  1. The demo firmware contains no serial code. Serial.begin() sits behind #if DEBUG_SERIAL, and the infer_nn build target sets it to 0. The call is not compiled into the binary — verifiable by inspecting the build flags rather than by trusting a promise.
  2. The build flag is a named target, not a hand edit. It cannot be forgotten, because selecting the demo target is what sets it.
  3. The wand runs on battery. During the demonstration no USB cable is connected, which makes the point visible to the judges without requiring them to read any code. If the budget forces the power-bank option in §3.2, this argument weakens and should be replaced by showing the build flags.

If the wand you build is not the wand this report describes

Three numbers in shared/wand_config.h describe the physical object: WAND_LENGTH_M, SENSOR_FROM_TIP_M and SENSOR_FROM_BUTT_M. If the tube ends up a different length, or the sensor lands somewhere else along it, change them there — not in the generator — then regenerate the corpus, re-run the audit, and re-run both Stage 1 sweeps. Everything downstream follows, because nothing downstream re-types those numbers. A wand whose geometry differs from its config file will still train, still run, and still classify; it will simply do so slightly worse, for reasons nothing will report.
